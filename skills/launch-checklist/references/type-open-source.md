# Open-source projects

From the core checklist, categories A (licensing parts), C12, C13, C16, J and K apply most. Hosting, billing and email items usually do not, unless the project also runs a service.

- [ ] **OSS1 [CRITICAL] Choose a licence and add the LICENSE file.** Pick a licence that matches the intent for commercial use, modification and patent grants, and use its standard text. Why: code without a licence gives nobody the right to use it. Verify: the LICENSE file is at the repository root, and the licence identifier is in the package metadata.
- [ ] **OSS2 [CRITICAL] Confirm the right to publish the code.** Check the employer's or client's claim on the work, third-party code copied in, and the compatibility of dependency licences with the chosen licence. Why: publishing code you do not own, or mixing incompatible licences, is hard to undo. Verify: written permission where needed, and a dependency licence report. Needs: A12, A13.
- [ ] **OSS3 [CRITICAL] Clean the repository history before making it public.** Scan every commit for secrets, internal addresses, customer data and personal information, and rotate anything found. Why: history is public forever once pushed, and forks keep copies. Verify: a full-history secret scan is clean, or the project is published from a fresh history.
- [ ] **OSS4 [HIGH] Write a README that gets someone to first use.** State what the project is, who it is for, how to install and run it, a minimal example, the status and how to get help. Why: the README decides whether a visitor tries the project. Verify: a person new to the project follows it on a clean machine.
- [ ] **OSS5 [HIGH] Add CONTRIBUTING.md.** Explain how to set up, test, propose changes and what will and will not be accepted. Why: clear expectations save maintainers' and contributors' time. Verify: a first-time contributor can run the tests from the instructions.
- [ ] **OSS6 [MEDIUM] Add a code of conduct with a contact.** Why: sets expectations for behaviour and gives a route for reports. Verify: the file exists and the contact address is monitored.
- [ ] **OSS7 [HIGH] Add SECURITY.md and turn on private vulnerability reporting.** State the supported versions and how to report privately. Why: without a private route, vulnerabilities are reported in public issues. Verify: the security policy shows on the repository and a test report reaches the maintainers.
- [ ] **OSS8 [MEDIUM] Add issue and pull request templates.** Why: structured reports contain the information needed to act. Verify: opening a new issue shows the template.
- [ ] **OSS9 [HIGH] Run tests and checks in CI on every pull request, with safe permissions.** Give workflows read-only permissions by default, and keep secrets away from code in pull requests from forks. Why: public CI runs untrusted code. Verify: a pull request from a fork runs the checks without access to secrets.
- [ ] **OSS10 [HIGH] Protect the main branch.** Require review and passing checks, and block force pushes. Why: prevents accidental or malicious direct changes. Verify: the branch protection settings show the rules.
- [ ] **OSS11 [HIGH] Automate releases and follow semantic versioning.** Tag releases, generate release notes and publish artifacts from CI. Why: manual releases drift and are a supply chain risk. Verify: a tag produces a release with notes and artifacts.
- [ ] **OSS12 [HIGH] Secure publishing to package registries.** If: the project publishes packages. Turn on two-factor login, publish from CI using the registry's trusted publishing where available, and record provenance. Why: hijacked maintainer accounts are a major supply chain attack route. Verify: the registry account and publishing configuration match the registry's current security guidance.
- [ ] **OSS13 [MEDIUM] Keep a changelog.** Why: users need to know what changed before upgrading. Verify: the launch version has an entry.
- [ ] **OSS14 [MEDIUM] Manage dependencies.** Commit lockfiles where appropriate, enable automated update alerts and state the supported runtime versions. Why: users inherit your dependencies' vulnerabilities. Verify: update alerts are on and the supported versions are tested in CI.
- [ ] **OSS15 [MEDIUM] Set repository metadata.** Description, topics, website link, social preview image and a contact for the maintainers. Why: helps people find and assess the project. Verify: the repository page shows each.
- [ ] **OSS16 [MEDIUM] State the governance and support expectations.** Say who maintains the project, how decisions are made and what response time to expect. Why: sets realistic expectations and reduces maintainer strain. Verify: the README or a governance file covers it.
- [ ] **OSS17 [MEDIUM] Decide the contribution licensing terms.** Choose between inbound contributions under the project licence, a sign-off requirement or a contributor agreement. Why: affects the ability to relicense later. Verify: the choice is stated in CONTRIBUTING.md.
- [ ] **OSS18 [LOW] Add funding and community links.** If: wanted. Why: gives supporters and users a place to go. Verify: the links work.
- [ ] **OSS19 [MEDIUM] Check the project name for conflicts.** Search package registries and trademark registers. Why: a name clash on a registry or with a trademark forces a rename. Verify: the name is available on each target registry.
