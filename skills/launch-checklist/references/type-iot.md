# IoT and hardware-connected software

Devices in the field are the least reversible release channel. A bad firmware update can disable hardware permanently, and physical products carry safety and regulatory duties that software alone does not. Product security and radio rules differ by country and are changing; check the jurisdictions and sources references and the regulator's own pages for each market. Recommend professional compliance advice for any device sold to the public.

- [ ] **IOT1 [CRITICAL] Build secure over-the-air updates with rollback.** Sign firmware, verify the signature on the device, keep a known-good image to fall back to, and survive power loss during an update. Why: this is the only way to fix devices after sale, and a faulty updater can disable them permanently. Verify: interrupt an update by cutting power and confirm recovery, and confirm an unsigned image is refused.
- [ ] **IOT2 [CRITICAL] Give every device a unique identity and credentials.** Provision unique keys or certificates at manufacture and ship no shared or default passwords. Why: shared credentials let one compromised device expose all of them, and several markets ban default passwords. Verify: extract credentials from two devices and confirm they differ.
- [ ] **IOT3 [CRITICAL] Stage firmware rollouts.** Release to a small group, watch health metrics, then widen, with the ability to halt. Why: limits the damage of a bad update. Verify: the rollout system can target a percentage and stop.
- [ ] **IOT4 [CRITICAL] Meet the regulatory and certification requirements for each market.** Cover radio, electrical safety, electromagnetic compatibility, product security and environmental rules. Why: selling uncertified devices is unlawful in most markets, and certification has long lead time. Verify: the certificates and declarations for each market are on file. Needs: A2.
- [ ] **IOT5 [CRITICAL] Secure the device.** Enable secure boot, disable debug interfaces in production, protect stored keys and encrypt communication with server authentication. Why: attackers have physical access to devices. Verify: production units refuse unsigned firmware and expose no open debug port.
- [ ] **IOT6 [CRITICAL] Assess physical safety and fail safely.** If: the device controls anything that can cause harm. Define the safe state on software failure, connection loss and power loss. Why: software faults in physical systems can injure people. Verify: a safety review is documented and each failure mode has been tested.
- [ ] **IOT7 [HIGH] Publish the security update period and a vulnerability reporting contact.** Why: buyers and several regulations expect a stated support period and a disclosure route. Verify: both are published.
- [ ] **IOT8 [HIGH] Work without the cloud where the user would expect it.** Handle lost connectivity, queue data and keep local control for essential functions. Why: connections and cloud services fail. Verify: disconnect the network and use the essential functions.
- [ ] **IOT9 [HIGH] Test the setup and pairing experience with ordinary users.** Why: setup is where most returns begin. Verify: people unfamiliar with the product complete setup, with the time and failure points recorded.
- [ ] **IOT10 [HIGH] Monitor the fleet.** Track connectivity, firmware versions, error rates, battery and resets, with alerts. Why: field problems appear as patterns across devices. Verify: a fleet dashboard shows each measure by firmware version.
- [ ] **IOT11 [HIGH] Test at fleet scale.** Simulate the expected number of devices connecting, reconnecting together after an outage and updating. Why: mass reconnection after an outage can overload the backend. Verify: a load test report covers a reconnection storm.
- [ ] **IOT12 [HIGH] Test in real conditions.** Cover weak signal, interference, temperature, battery drain, long uptime and clock drift. Why: lab conditions hide field failures. Verify: a soak test of several weeks on production hardware.
- [ ] **IOT13 [HIGH] Limit and disclose the data the device collects.** Pay attention to audio, video, location and presence data in homes and workplaces. Why: sensor data is highly sensitive. Verify: the data map covers every sensor and the privacy information is available before purchase and in setup. Needs: A1.
- [ ] **IOT14 [HIGH] Plan device lifecycle operations.** Cover ownership transfer, factory reset that wipes data, returns, decommissioning and end of service. Why: devices outlive their first owner and sometimes the company's service. Verify: a factory reset removes personal data and unlinks the account.
- [ ] **IOT15 [HIGH] Secure the manufacturing and provisioning process.** Control who can flash firmware and inject keys at the factory, and test each unit. Why: the factory is part of the security boundary. Verify: the provisioning procedure is documented and audited.
- [ ] **IOT16 [MEDIUM] Keep the companion app, firmware and backend compatible.** Define which versions work together and test the combinations. Why: users update the app and firmware at different times. Verify: a compatibility matrix is tested.
- [ ] **IOT17 [MEDIUM] Track open-source components and their licences in firmware.** Why: firmware often includes components whose licences require offering source code. Verify: a component list and the required notices ship with the product. Needs: A13.
