# Self-hosted and on-premise applications

Customers run this software on infrastructure you cannot see or reach. Each release is in use for a long time, upgrades happen on the customer's schedule, and support depends on what the customer can send you. Treat every release as irreversible.

- [ ] **SH1 [CRITICAL] Publish system requirements and supported environments.** State operating systems, container runtimes, databases and versions, hardware sizing by load, and network needs. Why: unsupported environments cause most installation failures. Verify: install on each supported environment from the published requirements alone.
- [ ] **SH2 [CRITICAL] Provide a tested installation path.** Offer container images, an orchestration chart, packages or an installer, with a quick start and a production guide. Why: installation is the customer's first experience. Verify: a person outside the team installs from the documentation on a clean machine.
- [ ] **SH3 [CRITICAL] Test upgrades from every supported version.** Include database migrations, skipped versions and a documented rollback or restore path. Why: a failed upgrade on a customer's server is the most expensive support case. Verify: upgrade from each supported version in CI and confirm the data is intact.
- [ ] **SH4 [CRITICAL] Ship secure defaults.** Generate secrets at install, force the first administrator to set a password, enable TLS guidance, and bind services to safe interfaces. Why: customers run the defaults. Verify: a fresh install has no default password and no service open that should be closed.
- [ ] **SH5 [CRITICAL] Sign and scan release artifacts.** Sign images and packages, publish checksums, scan for vulnerabilities and provide a software bill of materials where customers ask for it. Why: customers must be able to trust what they install. Verify: verify a signature using the documented steps, and review the scan report for the release.
- [ ] **SH6 [HIGH] Document every configuration option.** Give defaults, valid values and which changes need a restart, and validate configuration at start with clear errors. Why: misconfiguration is the main cause of support requests. Verify: start with a wrong value and read the message.
- [ ] **SH7 [HIGH] Document backup, restore and disaster recovery for customers.** Why: the customer owns the data and the recovery. Verify: follow the guide to back up and restore an instance.
- [ ] **SH8 [HIGH] Provide health checks, metrics and logs in standard formats.** Why: customers need to connect the product to their own monitoring. Verify: the endpoints and log format are documented and work.
- [ ] **SH9 [HIGH] Build a support bundle that redacts secrets.** Collect versions, configuration, logs and diagnostics in one command. Why: you cannot sign in to the customer's server. Verify: generate a bundle and confirm it contains no secret.
- [ ] **SH10 [HIGH] Publish the version support and security update policy.** State how long each version is supported, how security fixes are announced and how to subscribe. Why: customers plan upgrades around it. Verify: the policy and a security announcement channel exist.
- [ ] **SH11 [HIGH] Support restricted networks.** If: customers run without internet access. Provide offline installation, a way to mirror images and no required outbound calls. Why: many on-premise customers are air-gapped. Verify: install and run with outbound access blocked.
- [ ] **SH12 [HIGH] Make telemetry and update checks opt-in or clearly controllable.** Why: undisclosed outbound calls from a customer's network break trust and sometimes contracts. Verify: with them disabled, the product makes no outbound request.
- [ ] **SH13 [HIGH] Implement licence enforcement that fails gently.** If: the product is licensed. Handle expiry with warnings and a grace period, and work offline. Why: a licence fault that stops a customer's production is a serious incident. Verify: let a test licence expire.
- [ ] **SH14 [HIGH] Support the identity systems customers use.** If: selling to businesses. Offer single sign-on and directory integration. Why: it is a common purchase requirement. Verify: connect a test identity provider.
- [ ] **SH15 [MEDIUM] Document scaling and high availability.** Why: larger customers ask before buying. Verify: the documented topology has been tested.
- [ ] **SH16 [MEDIUM] Test compatibility and publish it.** Cover database versions, proxies, storage backends and orchestration versions. Why: customers upgrade their infrastructure independently. Verify: a compatibility table is published and tested in CI.
- [ ] **SH17 [MEDIUM] Write release notes that flag breaking changes and required actions.** Why: administrators read them before upgrading. Verify: the launch release notes include an upgrade section.
