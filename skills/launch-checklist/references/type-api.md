# APIs and backend services

A public API is a contract. Once others build on it, changes are hard to undo, so decisions about naming, errors and versioning matter more before launch than after.

- [ ] **API1 [CRITICAL] Authenticate every request and scope every credential.** Use API keys, tokens or signed requests, with scopes or roles limiting what each can do. Why: an unauthenticated or over-powerful credential exposes everything. Verify: requests without credentials, with a revoked key and with an insufficient scope are all refused.
- [ ] **API2 [CRITICAL] Manage API keys safely.** Show a key once, store only a hash, let customers rotate and revoke keys, and separate test and live keys. Why: keys leak, and customers need a way to respond. Verify: create, rotate and revoke a key, and inspect how keys are stored.
- [ ] **API3 [CRITICAL] Rate-limit by key and by IP, and document the limits.** Return a clear status and retry guidance when the limit is hit. Why: protects the service and gives clients predictable behaviour. Verify: exceed the limit and read the response.
- [ ] **API4 [HIGH] Choose a versioning policy before the first public release.** Decide how versions are expressed, what counts as a breaking change and how long old versions are supported. Why: without a policy, every change risks breaking customers. Verify: the policy is published in the documentation.
- [ ] **API5 [CRITICAL] Validate every request against a schema.** Reject unknown or malformed fields with a clear error, and limit body size and nesting depth. Why: unvalidated input leads to injection, crashes and corrupt data. Verify: send malformed, oversized and unexpected payloads to each endpoint.
- [ ] **API6 [HIGH] Use one consistent error format and correct status codes.** Include a machine-readable code, a human message and a request identifier. Why: clients write error handling once and rely on it. Verify: trigger each error class and compare the responses.
- [ ] **API7 [HIGH] Keep responses consistent.** Use the same naming, date format, pagination, filtering and null handling across endpoints. Why: inconsistency becomes permanent once clients depend on it. Verify: review the specification for each endpoint against a short style guide.
- [ ] **API8 [HIGH] Publish accurate documentation with examples.** Include authentication, every endpoint, errors, limits, a quick start and a machine-readable specification. Why: for an API, the documentation is the interface. Verify: a developer new to the API makes a successful call using the documentation alone, and the specification is checked against the running service.
- [ ] **API9 [HIGH] Support idempotency for operations that create or charge.** Accept an idempotency key or make the operation naturally safe to repeat. Why: clients retry on timeouts, and duplicates cost money. Verify: send the same request twice and confirm one result.
- [ ] **API10 [HIGH] Sign outgoing webhooks and retry them.** If: the API sends webhooks. Sign each payload, include a timestamp, retry with backoff, and let customers see and replay deliveries. Why: receivers need to trust and recover events. Verify: verify a signature with the documented method, and fail a delivery to watch the retries.
- [ ] **API11 [HIGH] Paginate and bound every list endpoint.** Why: an unbounded list becomes an outage as data grows. Verify: request a large collection and confirm a maximum page size is enforced.
- [ ] **API12 [HIGH] Monitor per endpoint and per customer.** Track request rate, errors and latency, and alert on changes. Why: an aggregate view hides one broken endpoint or one abusive client. Verify: the dashboard can be filtered by endpoint and by key.
- [ ] **API13 [HIGH] Test backward compatibility in CI.** Compare the specification against the previous release and fail on breaking changes. Why: accidental breaking changes are the main cause of customer incidents. Verify: remove a field in a test branch and see the check fail.
- [ ] **API14 [MEDIUM] Provide a sandbox or test mode.** Why: customers need to integrate without touching real data or money. Verify: complete an integration against the sandbox.
- [ ] **API15 [MEDIUM] Publish a deprecation and change communication process.** Use a changelog, advance notice and response headers for deprecated endpoints. Why: customers need time to adapt. Verify: the process is documented and a channel for announcements exists.
- [ ] **API16 [HIGH] Set timeouts, limits and circuit breakers on calls to other services.** Why: one slow dependency can exhaust the whole service. Verify: slow down a dependency in staging and confirm the service stays responsive.
- [ ] **API17 [MEDIUM] Check GraphQL-specific limits.** If: the API is GraphQL. Limit query depth and cost, and decide whether introspection is open in production. Why: a single expensive query can take down the service. Verify: send a deeply nested query and confirm it is refused.
