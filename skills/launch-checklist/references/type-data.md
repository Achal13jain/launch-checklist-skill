# Data science and data engineering projects

Published data is hard to recall. Once a wrong number reaches a dashboard, a report or a downstream system, people act on it, so correctness checks before publication matter more than speed.

- [ ] **DATA1 [CRITICAL] Make pipelines safe to run again.** Design each step so that repeating it gives the same result with no duplicates. Why: retries and re-runs are routine, and non-repeatable steps corrupt data. Verify: run a pipeline twice for the same period and compare row counts and totals.
- [ ] **DATA2 [CRITICAL] Add data quality tests that block bad data.** Check schema, uniqueness, null rates, ranges, referential integrity and freshness, and stop the pipeline when a critical check fails. Why: silent bad data is worse than a visible failure. Verify: inject a bad record in a test run and see the pipeline stop.
- [ ] **DATA3 [CRITICAL] Reconcile outputs against the source of truth.** Compare key totals with the source systems or finance figures. Why: a pipeline can run without error and still be wrong. Verify: a reconciliation report shows matching totals within a stated tolerance.
- [ ] **DATA4 [CRITICAL] Control access to sensitive data.** Classify the data, restrict access by role, mask or tokenise personal fields, and log access. Why: analytics stores gather sensitive data from many systems in one place. Verify: a user without the role cannot query the restricted columns. Needs: A1.
- [ ] **DATA5 [HIGH] Plan and test backfills.** Why: historical loads are larger and stress systems differently from daily runs. Verify: a backfill for a sample period completes within the expected time and matches.
- [ ] **DATA6 [HIGH] Handle late, missing and duplicate source data.** Why: sources deliver late and resend. Verify: simulate a late file and a resent file.
- [ ] **DATA7 [HIGH] Handle schema changes in sources.** Detect added, removed and retyped columns and alert before loading. Why: upstream teams change schemas without notice. Verify: change a column in a test source and see the alert.
- [ ] **DATA8 [HIGH] Monitor pipelines and alert on failure and lateness.** Track run status, duration, row counts and freshness, with an owner for each alert. Why: a pipeline that fails silently leaves stale data on dashboards. Verify: fail a run in staging and confirm the alert.
- [ ] **DATA9 [HIGH] Record lineage and definitions.** Document where each table and metric comes from and how each metric is calculated. Why: two definitions of the same metric destroy trust in the numbers. Verify: each published metric has one written definition and owner.
- [ ] **DATA10 [HIGH] Version transformations and deploy them through review.** Keep queries, models and notebooks that feed production in version control with tests. Why: unreviewed edits to production logic cause most data incidents. Verify: production jobs run from the repository, with no hand-edited copies.
- [ ] **DATA11 [HIGH] Apply retention and deletion to the data platform.** Propagate user deletion requests into warehouses, lakes, extracts and backups. Why: copies in analytics systems are covered by the same privacy rights. Verify: delete a test user at the source and confirm removal downstream. Needs: A8.
- [ ] **DATA12 [HIGH] Control cost.** Set query and storage budgets, partition and cluster large tables, and stop runaway queries. Why: usage-priced warehouses can produce large bills from one bad query. Verify: budget alerts and query limits are set. Needs: N1.
- [ ] **DATA13 [HIGH] Validate dashboards and reports with their users.** Check numbers, filters, time zones, currency and access rights. Why: the output is judged on whether people trust it. Verify: a business owner signs off each report against known figures.
- [ ] **DATA14 [MEDIUM] Make analyses reproducible.** If: the deliverable is an analysis or study. Pin the environment, data snapshot and seeds, and keep the code with the result. Why: findings that cannot be reproduced cannot be defended. Verify: another person re-runs the analysis and gets the same result.
- [ ] **DATA15 [MEDIUM] Define service levels and a run schedule.** State when data is ready each day and what happens when it is late. Why: downstream users plan around delivery time. Verify: the commitment is written down and monitored.
- [ ] **DATA16 [MEDIUM] Write the recovery procedure.** Cover re-running a failed day, restoring a table and correcting published figures. Why: corrections need to be fast and communicated. Verify: restore a dropped test table.
