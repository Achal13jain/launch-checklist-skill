# Mobile applications

A store release cannot be rolled back. A bad build stays on devices until users install an update, so testing before submission matters more than for web. Store rules change often; read the current policy pages listed in the sources reference before submission and record the date.

- [ ] **MOB1 [CRITICAL] Enrol in the developer programmes under the right legal entity.** Complete identity or organisation verification for each store. Why: enrolment has lead time and the account name is shown publicly as the seller. Verify: each account is active and owned by the business, with two-factor login.
- [ ] **MOB2 [CRITICAL] Read the current store review guidelines and check the app against them.** Pay attention to payments, account deletion, user content, sign-in options, permissions and minimum functionality. Why: rejection delays launch by days or weeks. Verify: a written pass through the current guideline headings, with the date read.
- [ ] **MOB3 [CRITICAL] Meet the store's current technical requirements.** Check the required target operating system level, build tools and binary format for new submissions. Why: builds that miss the current requirement are refused at upload. Verify: the build settings match the store's current requirements page.
- [ ] **MOB4 [CRITICAL] Secure and back up the signing keys.** Store the signing keys and certificates in a protected location with a second holder, and understand the store's key management option. Why: a lost signing key can make it impossible to update the app. Verify: a second person can produce a signed release build.
- [ ] **MOB5 [CRITICAL] Complete the store privacy declarations accurately.** Declare the data the app and every bundled SDK collects, and link a privacy policy. Why: wrong declarations lead to rejection or removal. Verify: compare the declaration with the data map and with each SDK's own disclosure. Needs: A1, A3.
- [ ] **MOB6 [CRITICAL] Request only the permissions the app needs, at the moment they are needed, with a clear reason.** Why: unnecessary permissions cause rejection and lose users at the prompt. Verify: list each permission in the manifest with the feature that needs it, and deny each one to confirm the app still works.
- [ ] **MOB7 [CRITICAL] Provide account deletion as the stores require.** If: the app allows account creation. Why: stores set rules for deleting an account from inside the app or from a web link. Verify: delete a test account using the route described in the current store rule.
- [ ] **MOB8 [CRITICAL] Follow the store's payment rules.** If: the app sells digital goods or subscriptions. Check which purchases must use the store's billing system and which may not, in each region. Why: the wrong payment method is a common rejection reason, and the rules differ by region and change. Verify: the purchase flow matches the current policy page, and a sandbox purchase, renewal, cancellation and restore all work.
- [ ] **MOB9 [HIGH] Set up crash and error reporting with symbol files.** Why: store crash data arrives late and with little detail. Verify: a forced test crash appears in the reporting tool with a readable stack trace.
- [ ] **MOB10 [HIGH] Test on a range of real devices and operating system versions.** Cover small and large screens, the oldest supported version, low memory, tablets if supported, and different system text sizes. Why: device variety is the main source of mobile bugs. Verify: the main journeys pass on each device in the written support matrix.
- [ ] **MOB11 [HIGH] Test poor network and offline behaviour.** Cover no connection, slow connection, switching networks and returning from the background. Why: mobile connections drop constantly. Verify: use the app in aeroplane mode and on a throttled connection with no data loss.
- [ ] **MOB12 [HIGH] Build a forced-update and minimum-version mechanism.** Let the server tell old versions to update, and keep the API compatible with every version still in use. Why: this is the mobile substitute for rollback. Verify: mark a test version as unsupported and see the update prompt.
- [ ] **MOB13 [HIGH] Use a staged release and pre-release testing track.** Release to testers first, then to a percentage of users. Why: limits the damage of a bad build. Verify: the release plan names the tracks and percentages, and any store testing requirement for new accounts is met.
- [ ] **MOB14 [HIGH] Test push notifications.** If: the app uses them. Cover permission, delivery in foreground and background, tapping through to the right screen, opting out and token refresh. Why: notifications are easy to break and annoying when wrong. Verify: send each notification type to real devices on both platforms.
- [ ] **MOB15 [HIGH] Test deep links and app links.** If: the app uses them. Cover installed and not-installed cases, and links from email and messages. Why: broken links strand users arriving from campaigns. Verify: open each link type on real devices.
- [ ] **MOB16 [HIGH] Protect data on the device and in transit.** Keep tokens in the platform's secure storage, keep secrets out of the app binary, and avoid logging personal data. Why: anything shipped in the app can be extracted. Verify: inspect the built package for keys, and check where tokens are stored.
- [ ] **MOB17 [HIGH] Prepare the store listing.** Name, subtitle, description, keywords, screenshots for each required size, preview video, category, age rating, support URL and contact. Why: the listing decides both approval and installs. Verify: every required field is complete and the screenshots show the current app.
- [ ] **MOB18 [HIGH] Give reviewers what they need.** Provide a working demo account, instructions and notes for anything that needs hardware or special access. Why: reviewers who cannot sign in reject the app. Verify: sign in with the demo account on a clean device.
- [ ] **MOB19 [MEDIUM] Measure start time, size, battery and memory.** Why: slow or heavy apps are uninstalled and reviewed badly. Verify: record the cold start time and download size for the release build.
- [ ] **MOB20 [MEDIUM] Check accessibility on each platform.** Test with the platform screen readers, large text and sufficient touch target sizes. Why: required for many users and by some laws. Verify: complete the main journey with the screen reader on.
- [ ] **MOB21 [MEDIUM] Plan how to answer store reviews and handle removal.** Why: early reviews set the rating, and a policy notice needs a fast reply. Verify: someone is named to monitor reviews and store messages.
