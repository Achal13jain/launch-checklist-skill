# Cloud infrastructure and platforms

Applies when the deliverable is the infrastructure itself: a landing zone, a platform for other teams, a cluster or a managed environment. Each cloud provider publishes a well-architected framework, listed in the sources reference; use the current version for the provider in use and verify service limits, defaults and prices on the provider's own pages or in the account.

- [ ] **INF1 [CRITICAL] Define all infrastructure as code, under review.** Keep the definitions in version control, apply them through a pipeline and avoid manual console changes. Why: hand-built infrastructure cannot be reviewed, repeated or recovered. Verify: rebuild a non-production environment from the code alone, and run a drift check on production.
- [ ] **INF2 [CRITICAL] Protect and back up the infrastructure state.** Store state remotely with locking, encryption, versioning and restricted access. Why: lost or corrupted state can make the infrastructure unmanageable, and state files hold secrets. Verify: the state backend shows locking and versioning, and access is limited to the pipeline and named administrators.
- [ ] **INF3 [CRITICAL] Secure the root and administrator accounts.** Turn on multi-factor login, remove long-lived root keys, use single sign-on with short-lived roles and keep a tested emergency access procedure. Why: these accounts can delete everything. Verify: review the provider's identity report for root usage, keys and multi-factor status.
- [ ] **INF4 [CRITICAL] Apply least privilege to people, services and pipelines.** Scope roles to what each needs, and replace long-lived keys with short-lived credentials. Why: over-broad roles turn a small compromise into a full one. Verify: run the provider's access analysis tool and resolve the findings.
- [ ] **INF5 [CRITICAL] Check for public exposure.** Review storage buckets, databases, snapshots, management ports and security group rules open to the internet. Why: publicly exposed storage and databases are the most common cloud breach. Verify: a scan of the account lists no unintended public resource.
- [ ] **INF6 [CRITICAL] Separate environments and limit the blast radius.** Use separate accounts, subscriptions or projects for production and non-production, with guardrail policies. Why: separation contains mistakes and breaches. Verify: a non-production credential cannot touch a production resource.
- [ ] **INF7 [CRITICAL] Turn on audit logging and keep it tamper-resistant.** Record control plane activity for all regions in a separate, restricted log store with retention. Why: without it, incidents cannot be investigated. Verify: find a recent administrative action in the log store.
- [ ] **INF8 [HIGH] Design the network deliberately.** Plan address ranges, segmentation, private connectivity to managed services, egress control and DNS. Why: network layout is hard to change later. Verify: a diagram matches the deployed network, and private resources have no public route.
- [ ] **INF9 [HIGH] Encrypt data at rest and in transit, and manage the keys.** Decide key ownership, rotation and who can use each key. Why: required by most standards and customers. Verify: the encryption settings are on for each data store and key access is restricted.
- [ ] **INF10 [HIGH] Manage secrets centrally with rotation.** Why: secrets in variables, images and state spread quickly. Verify: no secret appears in the code, images or pipeline logs.
- [ ] **INF11 [HIGH] Set budgets, alerts and tagging.** Tag resources by owner, environment and cost centre, and alert on spend and anomalies. Why: cloud cost grows unnoticed without ownership. Verify: every resource carries the required tags and budget alerts reach an owner. Needs: N1.
- [ ] **INF12 [HIGH] Check quotas and limits for launch capacity.** Why: default quotas stop scaling at the worst moment, and increases take time. Verify: compare the expected peak with current quotas in each region.
- [ ] **INF13 [HIGH] Design for failure of a zone, and decide about regions.** Spread across zones, test failover and state the recovery objectives. Why: zone failures happen. Verify: remove a zone or node in a test and watch the service recover. Needs: L3.
- [ ] **INF14 [HIGH] Back up data stores and test restores, including across accounts.** Why: backups in the same account can be deleted with it. Verify: restore from a backup held in a separate account or with deletion protection.
- [ ] **INF15 [HIGH] Monitor infrastructure and platform services with alerts and runbooks.** Why: an alert without a runbook delays the response. Verify: each alert links to a runbook and reaches an on-call person.
- [ ] **INF16 [HIGH] Harden and patch images, nodes and clusters.** Use minimal base images, scan them, patch on a schedule and apply the provider's cluster hardening guidance. Why: unpatched images accumulate known vulnerabilities. Verify: the image scan report and the patch schedule exist.
- [ ] **INF17 [HIGH] Add policy checks to the pipeline.** Scan infrastructure code for misconfiguration before it is applied. Why: catches public buckets and open ports before they exist. Verify: a deliberately insecure change is blocked.
- [ ] **INF18 [MEDIUM] Document the platform for the teams that use it.** Explain how to get an environment, deploy, get access and ask for help. Why: a platform is a product with users. Verify: a team onboards from the documentation.
- [ ] **INF19 [MEDIUM] Map the controls to the compliance standards that apply.** If: customers or regulators require a standard. Why: evidence is easier to collect from the start. Verify: a control mapping exists and the provider's compliance reports are on file.
- [ ] **INF20 [MEDIUM] Rehearse disaster recovery.** Why: plans fail on details that only a rehearsal shows. Verify: a dated exercise report with the measured recovery time.
